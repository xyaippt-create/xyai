# HDDE｜影界单阶段开发执行器

## 1. 唯一职责

一次只执行一个已经正式定义的 HDDE 开发阶段，并在同一次连续执行中完成：

现状读取
→ 基线核验
→ 受保护成果登记
→ 真实问题定位
→ 最低必要实现
→ 真实运行
→ 直接相关验证
→ 工作区完整性复查
→ 最终阶段报告

本 Skill 只规定“怎么执行”。

它不自行决定：

- 下一版本做什么；
- 产品优先级；
- 商业模式；
- 是否改变产品路线；
- 是否启动新架构；
- 是否同时推进多个阶段。

## 2. 调用边界

仅在用户或阶段任务卡明确提供以下信息时执行：

1. 项目目录、当前分支和预期 HEAD；
2. 本阶段唯一核心目标；
3. 已确认的真实问题；
4. 不可破坏边界，包含受保护成果与 Git 权限；
5. 5—8 个面向结果的验收门禁；
6. 固定六项简短报告合同。

普通任务卡正文控制在 400—800 字；复杂任务原则上不超过 1200 字。不得写死必须修改的文件、组件结构、变量名称、逐步实现过程和大量测试细节；安全边界确需限定文件时，只能作为不可破坏范围，不得替代 Codex 对真实仓库的判断。

每条正式开发指令必须保留：

> 基于真实仓库自主判断最短、安全、可复用的实现路径；发现本指令中的技术假设不成立时，必须以代码事实纠正，不得机械照搬。

缺少会影响安全执行的关键字段、字段互相矛盾，或任务包含多个阶段时：

- 不修改任何文件；
- 不猜测；
- 返回 `TASK_CARD_INCOMPLETE`；
- 明确指出需要修正的字段；
- 只请求一张修正后的完整任务卡。

`TASK_CARD_INCOMPLETE` 是执行前门禁，不是阶段失败，也不是架构阻断。

## 3. 规则优先级

执行前按以下顺序读取并处理约束：

1. 用户当前明确指令；
2. 当前阶段任务卡；
3. 仓库根目录及就近目录的 `AGENTS.md`；
4. 当前代码、配置、测试和真实运行结果；
5. 当前正式项目文档；
6. 历史报告和历史记录。

历史文档不得覆盖当前代码事实。

当任务卡与永久安全边界冲突时，不得继续修改；报告冲突并返回 `TASK_CARD_INCOMPLETE`。

## 4. 一阶段一条主指令

每次调用只解决一个核心问题。

必须在一次连续执行中完成必要的：

- 现状读取；
- 问题定位；
- 代码修改；
- 真实运行；
- 最低必要验证；
- 最终报告。

不得把同一阶段拆成：

- 调查指令；
- 补丁指令；
- 审核指令；
- 补测试指令；
- 补证据指令；
- v2 / v3 / v4 连续修复链。

允许在同一次执行内部先规划再实施，但不得把可预见的普通工程步骤外包给下一条指令。

发现范围外问题时：

1. 记录证据；
2. 判断是否阻断当前阶段；
3. 不阻断则不修改；
4. 写入最终报告的“延后事项”。

## 4A. 路线图治理与阶段推进规则

### 4A.1 路线图权威来源

本 Skill 不保存项目的当前版本、当前阶段、当前状态、分支、HEAD、批次路径或下一条具体任务。

每次处理 HDDE 开发、审核、冻结或接管任务前，必须优先读取并相互核对：

1. 仓库中的当前正式产品路线图；
2. 当前版本计划；
3. 当前阶段报告；
4. 已冻结阶段结论；
5. 真实代码、产物和 Git 状态。

当前项目进度不得只根据 Skill 内置内容、历史聊天记录或记忆推断。动态状态继续保存在项目文档和阶段报告中。

仓库存在多个路线图或阶段状态来源时，必须先识别唯一有效来源。无法确定时，不修改、不推进，并请求正式来源或明确的用户决策。

### 4A.2 Skill 与路线图职责分离

项目正式路线图负责记录：

- 当前阶段及其目标；
- 已完成或已冻结阶段；
- 当前真实阻断；
- 阶段依赖；
- 当前唯一下一步任务。

本 Skill 只规定：

- 如何规划和执行单阶段任务；
- 如何限制修改范围；
- 如何设置验收门禁；
- 如何进行自动审核和人工复核；
- 如何判断既有受控状态；
- 是否需要调用 Playwright；
- 稳定规则是否具备回写条件。

Skill 中的稳定阶段依赖只约束推进顺序，不代表或替代项目当前状态。

### 4A.3 唯一下一步原则

每次阶段报告或自动审核完成后，只能确定一个下一步主任务。该任务必须由当前阶段真实结果、未通过的最高优先级门禁、正式路线图的阶段依赖和用户最新明确决策共同决定。

不得同时启动多个阶段，不得在同一指令中夹带下一阶段开发，不得因报告缺口扩张为新的独立阶段，也不得在当前阶段未收口时提前建设前端、正式路由或后续能力。

### 4A.4 阶段进入门禁

后一阶段只有在前一阶段的正式报告明确满足进入条件后才能开始。

以下情况均不得进入下一阶段：

- `BLOCKED`；
- `NOT_READY`；
- `PENDING_HUMAN_REVIEW`；
- `REVIEW_PACKAGE_READY` 但人工复核尚未完成；
- 项目报告使用 `PASS_WITH_KNOWN_ISSUE`，且已知问题属于下一阶段硬依赖；
- 证据不完整或状态真实性未证明。

这里对 `PASS_WITH_KNOWN_ISSUE` 的引用只用于识别外部项目报告中的未满足依赖，不新增或改变本 Skill 第 15 节的受控终态与状态语义。

### 4A.5 4K 阶段固定依赖

4K 能力按以下稳定顺序推进：

1. 传统 4K 基线与黄金样本冻结；
2. 保守 AI 4K 增强引擎 PoC；
3. 失真门禁与自动路由；
4. 正式单图产品闭环与前台界面；
5. 真实商业样本验证与版本收口。

阶段 2 未证明存在安全、稳定、可见的 AI 增益时，不得进入阶段 3。阶段 3 未形成可靠失真门禁与自动路由时，不得进入阶段 4。阶段 4 未完成真实前后端产品闭环和关键用户路径验证时，不得进入阶段 5。

该顺序是稳定依赖，不表示 Skill 保存任何阶段的当前状态。

### 4A.6 路线图变更规则

路线图调整必须先更新项目正式路线图，或形成明确的用户批准记录，随后才能调整开发任务。每次调整必须说明：

- 原路线；
- 新路线；
- 调整原因；
- 受影响阶段；
- 已冻结阶段是否受影响；
- 当前唯一下一步是否变化。

不得静默重开已冻结阶段。不得因单次实现缺陷、临时环境问题或报告格式问题直接改变产品总路线。

### 4A.7 Skill 回写条件

只有满足以下任一条件、且可跨版本或跨阶段稳定复用的新结论，才允许建议回写 Skill：

- 稳定产品原则；
- 稳定安全边界；
- 稳定状态语义；
- 稳定审核或冻结方法；
- 稳定 Playwright 调用规则。

阶段审核应在不改变既有状态字段和最终报告模板的前提下追加 `Skill迭代判断：需要更新 / 暂不需要更新`，并说明可复用规则、应更新的 Skill、更新范围及是否需要立即独立更新。实际回写必须作为独立、明确授权的 Skill 维护任务执行。

### 4A.8 禁止写入 Skill 的动态内容

不得将以下动态项目状态写入 Skill：

- 当前分支或 HEAD；
- 当前版本号；
- 当前阶段或当前阶段状态；
- 某次批次路径；
- 某次测试或审核数量；
- 某个临时缺陷；
- 一次性模型、参数或执行指令；
- 当前下一条具体任务。

## 5. 只读预检

任何修改前，必须读取并报告：

- 实际项目目录；
- 当前分支；
- 实际 HEAD；
- 预期 HEAD 对比；
- 产品版本；
- `git status --short`；
- staged、unstaged、untracked 状态；
- 是否满足 `STAGING_EMPTY: YES`；
- 当前已有差异；
- 与任务直接相关的文件、测试和运行入口；
- 仓库适用的 `AGENTS.md`。

不得假设工作区干净。

如果任务卡声明未提交成果属于受保护基线，应保护它们，而不是清理它们。

以下情况默认停止在修改前：

- 分支不匹配；
- HEAD 不匹配；
- staging 非空；
- 无法确认工作区差异归属；
- 受保护成果说明与实际状态冲突。

不得自动切换分支、reset、restore、stash 或清理来“修正”基线。

## 6. 受保护成果登记

修改前建立内部受保护清单，至少覆盖：

- 已有 tracked 修改；
- 已有 untracked 文件；
- 已完成但未提交的功能；
- 已冻结阶段成果；
- 正式用户文件和正式输出；
- 用户明确禁止覆盖的文件；
- 当前有效配置与设置；
- 已确认有效的测试或运行结果。

只在确有必要时记录关键 diff 或哈希，不为形式完整制造大规模证据。

任何后续操作都必须保留这份清单。

禁止：

- 未读取当前内容就整文件覆盖；
- 用旧版本覆盖当前工作区；
- 删除用途不明的文件或目录；
- 重新实现已完成成果；
- 因“与当前任务无关”而移除受保护差异；
- 通过清理工作区降低执行复杂度。

受保护成果发生任何损失，当前阶段直接禁止通过。

## 7. 真实根因定位

修改前必须建立可解释的真实故障链：

用户现象或运行问题
→ 触发条件
→ 实际执行路径
→ 失败点
→ 根因
→ 影响范围
→ 最小修复位置
→ 可观察验收结果

必须区分：

- 根因与表面症状；
- 当前正式代码与历史代码；
- 正式逻辑与测试夹具；
- 手写源码与生成文件；
- 产品缺陷与环境限制；
- 当前阶段问题与后续问题。

不得仅凭：

- 文件名；
- 搜索命中；
- 旧报告；
- 注释；
- 猜测；
- 单一报错表象

就宣布根因并大范围修改。

普通范围内问题应在同一次执行中完成诊断与修复，不单独产出调查阶段。

## 8. 最低必要实现

只修改与下列事项有直接关系的内容：

- 真实根因；
- 必要实现；
- 直接相关测试；
- 真实验收；
- 必要阶段记录。

优先：

- 复用现有架构；
- 复用现有路径选择、配置、API 与测试机制；
- 最小增量修改；
- 简单、可解释、可回退的实现；
- 删除明确错误或废弃机制，而不是叠加兼容层；
- 直接解决用户可见问题。

禁止：

- 借机重构无关模块；
- 顺手优化；
- 扩大产品范围；
- 同时进入下一版本；
- 新增未经验证的抽象层；
- 新增不必要依赖；
- 用复杂兼容逻辑保留已确认错误行为；
- 大范围格式化；
- 为小问题建设复杂测量器、审核器或报告系统；
- 用代码量、测试量或文档量代替真实产品结果。

普通开发任务默认投入尺度：

- 93%：真实代码修改、功能开发和用户结果；
- 5%：与本次改动直接相关的最低必要验证；
- 2%：一次简短审核和报告。

只有正式目录、数据迁移、原图安全、核心算法、版本冻结或发布候选等高风险任务，才允许提高验证比例，并必须说明原因。

禁止审核套审核、重复运行无关测试、为证明而扩张验证系统、重新打开已通过范围，或让报告工作量接近开发工作量。

职责分工、任务卡写法和执行纪律同时遵守：

- `references/01-development-discipline.md`

## 9. 真实运行与验证

静态检查不能单独支持 `PASS_AND_FROZEN`。

必须依据修改类型执行直接相关的真实验证。按需读取：

- `references/05-validation-routing.md`
- `references/03-acceptance-gates.md`

验证必须满足：

- 与改动直接相关；
- 足以证明验收门禁；
- 不超出必要范围；
- 来自真实命令、API、页面、日志、文件或处理结果；
- 能对应当前代码和当前工作区。

不得：

- 报告未实际执行的命令；
- 把“计划执行”写成“已经通过”；
- 用 Mock 结果替代正式结果；
- 用静态推测替代运行证据；
- 为简单改动新建复杂验证框架；
- 为追求全量覆盖拖延真实功能交付。

当改动跨越多个关键链路或高风险数据迁移时，可以扩大验证，但必须说明与验收门禁的直接关系。

当前任务范围内能直接解决的问题必须直接完成；只有具备真实代码或运行证据、且当前批准范围内没有安全方案的架构阻断才允许停止。

Playwright 只执行与当前改动直接相关的最低必要真实用户路径验证，不扩张为无关全量 E2E 或独立审核阶段。

正式用户界面的可见文字不得低于 12px。隐藏元素、测试代码和不会进入用户界面的技术值，不得为满足扫描结果进行无意义修改。

## 10. 失败分类

验证失败后先分类：

### A. 本阶段引入的回归

在不突破阶段范围的前提下修复并重新验证。

### B. 已存在的历史失败

提供前后证据，判断是否影响本阶段门禁。

不能因为“历史存在”就忽略其对当前结果的影响。

### C. 环境限制

报告具体环境、命令、错误和已尝试动作。

不得静默改用不等价验证。

### D. 真实架构阻断

仅当以下条件全部成立时允许：

- 根因有真实证据；
- 阻断当前阶段验收；
- 当前批准范围内没有安全方案；
- 继续必须改变架构、数据合同、迁移策略或产品规则；
- 普通调试和范围内修复已经完成；
- 继续执行将产生真实数据或产品风险。

普通 Bug、依赖缺失、测试失败、时间不足、调查不完整或执行不彻底，都不是架构阻断。

## 11. HDDE 永久产品边界

执行涉及对应模块时，必须读取：

- `references/02-project-boundaries.md`

重点包括：

- 正式目录唯一来源；
- 禁止项目临时目录回退；
- 原图和正式文件保护；
- 画质真实性；
- 用户可见命名；
- 日志真实性；
- 版本单一权威来源；
- 禁止 Mock、伪成功和不存在的能力。

这些规则不得被普通阶段任务静默改写。

改变永久产品边界必须先形成独立产品或架构决策，不属于普通执行阶段。

## 12. Git 与发布安全

未经当前任务卡逐项明确授权，禁止：

- `git add`；
- `git commit`；
- `git commit --amend`；
- `git push`；
- merge；
- rebase；
- Tag；
- Release；
- 删除分支；
- 切换分支；
- 修改远端状态；
- 创建或切换 worktree；
- stash；
- reset；
- clean；
- 覆盖式 restore 或 checkout。

永久禁止批量暂存：

- `git add .`
- `git add -A`
- `git add --all`

即使任务授权提交，也只能逐个显式暂存已审核文件，并在操作前重新核对差异。

默认硬门禁：

`STAGING_EMPTY: YES`

历史授权不会自动延续到下一阶段。

## 13. 文档与版本记录

仅在任务直接需要时更新文档。

正式版本档案只记录：

- 最终实现；
- 解决的问题；
- 最终验证；
- 遗留事项；
- 可验证基线。

不得写入：

- 单轮调试过程；
- 失败尝试流水；
- 截图堆叠；
- 重复的 build PASS；
- 无价值 diff 过程；
- 为证明工作量而产生的噪声。

无法可靠确认的历史事实不得写入正式档案。

## 14. 工作区完整性复查

实现和验证后必须：

1. 再次读取 Git 状态；
2. 检查相关 diff；
3. 与受保护清单对比；
4. 确认未丢失任何已有成果；
5. 列出全部实际修改和新增文件；
6. 确认无未经授权 Git 行为；
7. 确认 staging 仍为空；
8. 确认范围外模块未被修改；
9. 确认最终报告与当前工作区一致。

任何受保护成果损失、未授权操作、门禁未过或证据不一致，均禁止通过。

## 15. 最终结论

验证型 PoC 按合同完成后允许以下四类结果。`REVIEW_PACKAGE_READY` 与 `POC_VALUE_NOT_PROVEN` 必须由任务卡预先声明为允许终态；普通产品阶段不得使用这两个状态。普通实现失败继续使用本节定义的 `BLOCKED`，不属于验证型 PoC 的有效结论。

### `PASS_AND_FROZEN`

仅当以下条件全部满足：

- 唯一阶段目标已完成；
- 真实根因已解决；
- 受保护成果完整；
- 验收门禁全部通过；
- 必要真实运行通过；
- 直接相关测试通过；
- 没有实质性范围扩张；
- 没有未解决问题否定结论；
- 报告证据可以复核；
- 不需要继续下发同阶段修复指令。

“FROZEN”只表示阶段成果正式收口，不代表已经提交、合并、Tag 或发布。

对应字段必须为：

```text
STAGE_RESULT: PASS_AND_FROZEN
FINAL_STATUS: PASS
FREEZE_STATUS: FROZEN
AI_SAFE_GAIN_STATUS: PASS
SELF_AUDIT: PASS
```

### `REVIEW_PACKAGE_READY`

仅当以下条件全部满足：

- 任务卡预先声明人工视觉复核是阶段外部决策门禁；
- 代码、真实运行、技术验证与证据均已完成；
- 所有强制技术硬门禁均为 `PASS`；
- 所有结构安全门禁均为 `PASS`；
- 不存在 `REVIEW`、`UNKNOWN`、`FAIL` 或相互矛盾状态；
- 人工复核包及其执行矩阵、路径、哈希和复核说明完整；
- 受保护成果完整；
- 唯一未完成项是人工对真实视觉增益的判断；
- 尚未进入依赖该判断的下一阶段。

对应字段必须为：

```text
STAGE_RESULT: REVIEW_PACKAGE_READY
FINAL_STATUS: PENDING_HUMAN_VISUAL_REVIEW
FREEZE_STATUS: NOT_READY
AI_SAFE_GAIN_STATUS: PENDING_HUMAN_REVIEW
SELF_AUDIT: PASS
SELF_AUDIT_SCOPE: EXECUTION_AND_PACKAGE_CONTRACT_ONLY
```

该状态不是最终通过、不是冻结、不是架构阻断，也不是补充审核或拆分开发任务。用户人工复核属于任务卡预先声明的外部决策门禁，不构成第二条 Codex 开发指令；复核完成后可直接形成阶段结论，仅在发现真实代码缺陷时才新建修复任务。

### `POC_VALUE_NOT_PROVEN`

仅当以下条件全部满足时使用：

- PoC 任务卡要求的实现、运行、证据和人工视觉复核已经完整完成；
- 技术执行过程没有未解决的实现缺陷；
- 结构安全和视觉结果具有真实证据；
- 人工复核确认候选与传统基线持平、增益平庸、明显倒退或不具备商业价值；
- 负结论是技术假设未被验证，而不是代码执行失败；
- 不存在仍可在当前批准范围内修复的缺陷。

对应字段必须为：

```text
STAGE_RESULT: POC_VALUE_NOT_PROVEN
FINAL_STATUS: BLOCKED_NO_QUALITATIVE_GAIN
FREEZE_STATUS: NOT_READY
AI_SAFE_GAIN_STATUS: NOT_PROVEN
POC_CONTRACT_COMPLETED: YES
NEGATIVE_CONCLUSION_SUPPORTED_BY_EVIDENCE: YES
DEVELOPMENT_EXECUTION_FAILURE: NO
SELF_AUDIT_SCOPE: POC_EXECUTION_AND_EVIDENCE_CONTRACT_ONLY
SELF_AUDIT: PASS
```

此处 `SELF_AUDIT: PASS` 仅表示 PoC 按合同完整执行、负结论由真实证据支持、不是开发执行失败且报告与状态一致；不表示 AI 路线视觉质量通过、AI 增强具有产品价值、阶段可以冻结、可以进入下一阶段或 4K 核心路线已经成立。

这是验证型 PoC 的合法负结论，不得写成通过、冻结或真实架构阻断。`AI_SAFE_GAIN_STATUS: NOT_PROVEN` 只是增益结论，不自动决定阶段终态，也不得自动推导 `POC_VALUE_NOT_PROVEN` 或 `SELF_AUDIT: PASS`。若需重新设计路线，必须进入预先规划的新阶段，不得在原阶段追加修补链。

### `BLOCKED_BY_REAL_ARCHITECTURE`

仅在第 10 节 D 类条件全部成立时使用。

普通实现缺陷不得使用 `REVIEW_PACKAGE_READY`、`POC_VALUE_NOT_PROVEN` 或 `BLOCKED_BY_REAL_ARCHITECTURE` 规避修复。任一技术门禁为 `FAIL`、`REVIEW` 或 `UNKNOWN`，结构不安全，总体 `success` 与门禁矛盾，复核包、执行矩阵、哈希或路径证据不完整，存在路径逃逸，Alpha、拼接缝或结构问题未闭环，Settings 或受保护成果被修改，当前主指令、报告或证据合同未完成，或仍有本阶段可修复缺陷时，必须输出：

```text
STAGE_RESULT: BLOCKED
FINAL_STATUS: BLOCKED
FREEZE_STATUS: NOT_READY
SELF_AUDIT: FAIL
```

禁止使用模糊结论：

- PASS_WITH_NOTES
- PARTIAL_PASS
- MOSTLY_COMPLETE
- TEMPORARY_PASS
- PASS_PENDING_VALIDATION
- 先通过后补证据

## 16. 最终报告

必须使用：

- `assets/final-report-template.md`

最终报告统一为六项：

- `STATUS`
- `FILES_MODIFIED`
- `IMPLEMENTED`
- `VALIDATION`
- `BLOCKER`
- `PROTECTION`

不要输出冗长过程日志。

## 17. 执行优先级

1. 保护已有成果；
2. 解决当前唯一核心问题；
3. 用最低必要真实验证证明结果；
4. 如实报告；
5. 避免无价值工程扩张。

## 18. AI 增强 PoC 通用门禁

本节适用于生成式、感知型超分辨率及其他 AI 增强核心引擎 PoC。规则只描述跨阶段执行要求，不预设或否定任何具体模型、算法和候选架构。

### 18.1 候选路线级状态矩阵

存在多条 AI 候选路线时，必须逐路线独立记录：

- `TECHNICAL_STATUS`；
- `STRUCTURE_SAFETY_STATUS`；
- `VISUAL_GAIN_STATUS`；
- `ROUTE_DECISION`；
- `REJECTION_REASON`。

被淘汰路线必须记录真实拒绝原因；未被淘汰时，`REJECTION_REASON` 应明确为不适用。不得只用阶段级 `PASS` 掩盖任一路线的失败、待复核或未证明状态。

### 18.2 技术、结构与视觉价值三门禁

必须明确分离并依次判断：

1. 技术可运行：候选能真实执行，输出满足格式、尺寸、方向、透明度及必要完整性要求；
2. 结构安全：候选不改变文字、Logo、人物、产品、材质、色彩、光影和原始设计结构；
3. 肉眼可见真实增益：候选在完整画面、同语义 ROI 和原生 100% 局部中形成稳定、直接可见且有交付价值的提升。

技术通过不等于结构安全；结构安全也不等于具备视觉价值或产品化资格。

所有技术硬门禁必须来自真实测量结果、独立验证结果或可审计的实际执行轨迹。不得通过固定写入以下状态来替代真实验证：

- `cropped=false`；
- `stretched=false`；
- `padded=false`；
- `rotated=false`。

总体 `success` 必须由全部强制门禁共同计算。任一强制门禁为 `REVIEW`、`FAIL`、`BLOCKED` 或 `UNKNOWN` 时，总体 `success` 不得为 `true`。禁止出现 `success=true` 与 `tile_seam_precheck=REVIEW` 或其他门禁状态相互矛盾的结果。

### 18.3 安全但平庸的候选不得通过

候选出现以下任一情况时：

- 与传统基线整体接近；
- 只稍微更锐；
- 只在少量 ROI 略好；
- 只有指标提升；
- 必须极端放大才能看出差异；

必须按当前候选路线记录：

```text
VISUAL_GAIN_STATUS: NOT_PROVEN
ROUTE_DECISION: REJECTED_NO_GAIN
```

`VISUAL_GAIN_STATUS` 描述当前候选路线的视觉增益结论，`ROUTE_DECISION` 描述当前候选路线的最终去留。`AI_SAFE_GAIN_STATUS` 只能由阶段级聚合规则根据全部路线计算；单个候选路线不得直接赋值或覆盖该阶段级状态。

不得将其描述为路线成功、阶段通过、已形成质变或可以产品化。

### 18.4 AI 语义重构风险

生成式或感知型超分辨率路线必须重点检查：

- 中文笔画重构；
- 包装文字重构；
- Logo 轮廓漂移；
- 人物身份或五官重构；
- 产品结构变化；
- 虚假发丝、毛孔、材质或背景纹理；
- 原图不存在的锐化边和伪细节。

任一路线出现关键语义重构时，应淘汰该路线，不得因为清晰度更高而继续保留。某个具体模型或实现失败，只能否定该次候选，不得泛化为所有 AI 直出路线必然失败。

### 18.5 人工视觉冻结门禁

在 AI 增强核心引擎阶段：

- 自动指标只负责风险预检；
- Codex 只负责技术与结构初判；
- 最终视觉增益必须由人工查看完整画面、同语义 ROI 和原生 100% 局部后确认。

人工视觉复核前不得：

- 冻结 AI 主路线；
- 输出阶段最终 `PASS`；
- 进入自动路由；
- 接入正式产品闭环。

当任务卡预先声明人工视觉复核为外部决策门禁，且技术、结构、证据和复核包均已完成时，允许以以下状态结束 Codex 执行：

```text
STAGE_RESULT: REVIEW_PACKAGE_READY
FINAL_STATUS: PENDING_HUMAN_VISUAL_REVIEW
FREEZE_STATUS: NOT_READY
AI_SAFE_GAIN_STATUS: PENDING_HUMAN_REVIEW
SELF_AUDIT: PASS
SELF_AUDIT_SCOPE: EXECUTION_AND_PACKAGE_CONTRACT_ONLY
```

此处 `SELF_AUDIT: PASS` 仅表示执行与复核包契约完整、技术和结构门禁通过、报告内部一致且受保护成果安全；不表示视觉增益成立、产品价值成立、阶段最终通过、路线冻结或可以进入下一阶段。

人工视觉复核完成后，如未证明真实视觉增益，必须形成：

```text
STAGE_RESULT: POC_VALUE_NOT_PROVEN
FINAL_STATUS: BLOCKED_NO_QUALITATIVE_GAIN
FREEZE_STATUS: NOT_READY
AI_SAFE_GAIN_STATUS: NOT_PROVEN
POC_CONTRACT_COMPLETED: YES
NEGATIVE_CONCLUSION_SUPPORTED_BY_EVIDENCE: YES
DEVELOPMENT_EXECUTION_FAILURE: NO
SELF_AUDIT_SCOPE: POC_EXECUTION_AND_EVIDENCE_CONTRACT_ONLY
SELF_AUDIT: PASS
```

该结果仅适用于 PoC 合同、真实运行、证据和人工复核均已完成，且没有未解决实现缺陷时。`SELF_AUDIT: PASS` 只确认 PoC 执行与证据合同完整、负结论有真实证据且不是开发执行失败；不代表视觉质量通过、产品价值成立、阶段冻结或可以进入下一阶段。该结果不是 `BLOCKED_BY_REAL_ARCHITECTURE`。

路线级状态必须使用以下受控值：

- `VISUAL_GAIN_STATUS`：`NOT_RUN`、`NOT_PROVEN`、`PENDING_HUMAN_REVIEW`、`PASS`、`FAIL`；
- `ROUTE_DECISION`：`REJECTED_TECHNICAL`、`REJECTED_UNSAFE`、`PENDING_HUMAN_REVIEW`、`ACCEPTED`、`REJECTED_NO_GAIN`。

路线级聚合必须满足：

- 技术失败：`TECHNICAL_STATUS: FAIL`，`ROUTE_DECISION: REJECTED_TECHNICAL`；
- 技术通过但结构不安全：`STRUCTURE_SAFETY_STATUS: FAIL`，`ROUTE_DECISION: REJECTED_UNSAFE`；
- 技术与结构通过但待人工复核：`VISUAL_GAIN_STATUS: PENDING_HUMAN_REVIEW`，`ROUTE_DECISION: PENDING_HUMAN_REVIEW`；
- 人工确认真实增益：`VISUAL_GAIN_STATUS: PASS`，`ROUTE_DECISION: ACCEPTED`；
- 人工确认接近基线、平庸、回退或价值未证明：`VISUAL_GAIN_STATUS: NOT_PROVEN` 或 `FAIL`，`ROUTE_DECISION: REJECTED_NO_GAIN`。

不得从技术可运行自动推导视觉 `PASS`。

阶段级 `AI_SAFE_GAIN_STATUS` 必须按路线聚合：

- 至少一条路线经人工确认视觉增益并为 `ACCEPTED`：`PASS`；
- 没有路线经人工确认通过，但至少一条技术与结构均通过且待人工复核：`PENDING_HUMAN_REVIEW`；
- 没有任何路线通过或等待人工复核：`NOT_PROVEN`。

`NOT_PROVEN` 可用于人工复核完成但增益未证明、所有路线技术失败、所有路线结构不安全、所有路线均被淘汰，或没有路线具备进入人工复核资格的场景。它只是阶段级增益结论，不与 `STAGE_RESULT` 一对一自动映射；阶段终态还必须结合 PoC 合同是否完成、是否存在执行缺陷、人工视觉复核是否完成及是否属于真实架构阻断。

禁止所有路线已拒绝但阶段通过、路线仍待人工复核但阶段最终通过，或路线技术失败却声明阶段技术全部通过。

### 18.6 第三方模型归属与许可证

所有第三方模型、执行器和运行组件必须记录：

- 官方来源；
- 版本；
- 模型文件 SHA256；
- 执行器版本；
- 许可证；
- 修改情况；
- 再分发要求；
- 产品中需要保留的版权或许可证声明。

许可证来源或模型归属无法确认时，不得进入产品化。

### 18.7 故障探针路径安全

故障探针的所有写入路径必须：

- 先规范化为绝对真实路径；
- 严格位于已经批准的隔离临时根目录内；
- 拒绝绝对路径逃逸；
- 拒绝 `..` 路径穿越；
- 拒绝符号链接、目录联接或重解析点逃逸；
- 拒绝 Settings、正式目录、仓库目录和受保护产物路径。

必须逐一校验实际输出文件、记录文件及其他写入目标，不能只校验 `output_root` 而不校验实际 `record_path`。

### 18.8 Alpha 透明边缘真实性门禁

Alpha 安全不能只检查 Alpha 通道字节是否一致，还必须检查并记录：

- 半透明像素；
- Alpha 梯度边缘；
- 保护区域像素数量；
- 保护区域 RGB 变化像素数量；
- 最大 RGB 变化；
- 黑底合成结果；
- 白底合成结果；
- 黑白边或颜色污染。

图片存在透明梯度边缘但检测结果为 0 个保护像素时，必须判定门禁失败。

保护掩码经过高斯模糊、羽化、插值、形态学操作或融合权重扩散后，必须在最终融合前重新施加硬保护区。不得只在模糊或扩散前将保护权重置零。

### 18.9 AI PoC 报告执行矩阵

AI PoC 最终报告必须提供逐样本、逐路线执行矩阵，至少包含：

- `sample_id`；
- `route`；
- `source_path`；
- `baseline_path`；
- `candidate_path`；
- `runtime_seconds`；
- `output_size_bytes`；
- `dimensions`；
- `format`；
- `alpha_status`；
- `geometry_gate`；
- `tile_seam_gate`；
- `structure_safety_gate`；
- `technical_status`；
- `route_decision`。

不得只提供聚合数量或连续尺寸列表。
